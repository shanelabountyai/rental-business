| D-16 | **Vendor magic-link lifetime (R-025)** — amends "single-use" in ROLE-05, §6.1, §7 and §13 | **A vendor work-order link is scoped, expiring and revocable, but MULTI-USE until it expires — not single-use.** Single-use remains correct and unchanged for every other token purpose (tenant magic link, both password resets, the MFA challenge). | The PRD's "single-use" is right for a token whose job is to **establish** a longer-lived credential: a tenant magic link is redeemed once and becomes a session, so burning it costs the user nothing. A vendor link **is** the credential — there is no account and no session behind it (D-6) — so burning it on first click means the plumber who opened the text at 7am to accept the job cannot reopen it at 4pm to upload the invoice. That is not a hypothetical edge: accept-now / photograph-the-work-later / photograph-the-napkin-invoice-later is the *only* real vendor workflow, and it spans hours or days by nature. A single-use link would fail on the second step of every single job, and "the vendor phones the invoice in instead" is precisely the outcome D-6 exists to prevent — the backlog's own line for R-025 calls this item "the difference between a maintenance module vendors use and one they ignore." **The alternative considered and rejected** was single-use redemption into a work-order-scoped session cookie: it preserves the letter of "single-use" but dies on a cleared cookie, a second device, or simply re-clicking the original SMS days later, which is the most likely way a vendor returns. **What replaces single-use as the control set**, all of it built: the token is scoped to exactly ONE work order and grants nothing else anywhere in the product; it expires (3 days, `TOKEN_TTL_MINUTES.VENDOR_WORK_ORDER`); reissuing revokes every prior token for that work order, so a link believed compromised is killed by resending; every privileged action taken through it is audited with the vendor named as actor; and each access-code reveal is logged individually (PROP-03). Worth stating plainly: the status quo this replaces is an operator texting the address, gate code and tenant's phone number in cleartext with no expiry, no scope and no audit trail whatsoever — the link is strictly better than what it is displacing, on every one of those axes. |

| D-19 | **Verify & close: where the money is entered, and who owns a reopen (R-030)** | **The cost of a job is typed ONCE, on the work order, and every downstream reader computes from that row — there is no maintenance-spend table and never will be one.** A tenant's verification is its own append-only-in-practice row carrying **the vendor who did the work, captured at the moment of the answer**, not read off the work order later. | D-24 | **Webhook idempotency is a claim-before-project INSERT (R-034, D-11)** | **The `ProcessedStripeEvent` insert happens BEFORE the projection, and the Stripe event id is the PRIMARY KEY.** A duplicate delivery loses on the key and stops. Making the event id the primary key rather than a surrogate with a unique index is what makes the INSERT itself the lock. There is a test that fires three concurrent deliveries of one event and asserts exactly one projects. **Why ignored events still return 200**: Stripe retries anything else forever, and a dashboard full of red for events we deliberately did nothing with is a monitoring surface nobody will trust. They are recorded with a stated reason, because "we saw it and chose to do nothing" is an answer silence cannot give. **The handled-event list is deliberately closed and short** — `charge.*` is excluded alongside `invoice.*` specifically because projecting both would double-count every payment. |
