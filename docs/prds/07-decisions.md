# Decision Log — Single-Family Rental Operations Platform

**Status:** D-1 through D-10 recorded 2026-07-31 at project setup, carrying forward the conventions proven on the self-storage build. **D-11 (2026-07-31) supersedes D-2** and deliberately diverges from the storage platform. **D-13 (2026-08-01) settles the two-payer ledger shape** and closes OQ-12; OQ-2 is partially answered and R-048 remains gated on the rest of it. Open owner decisions are listed under "Needs owner decision"; several gate specific milestones.
**Precedence:** This document amends the PRDs. Where a PRD conflicts with a decision below, this document wins. When building from the backlog, treat each decision as settled — do not re-open unless the owner amends this log.

| # | Topic | Decision | What it means for the build |
|---|---|---|---|
| D-1 | Tech stack | **Same stack as the self-storage platform.** | Next.js (App Router) + TypeScript, Postgres + Prisma, Auth.js, Tailwind + shadcn/radix, Stripe, Resend, Vitest + Playwright + axe + Lighthouse CI, Vercel. Monorepo `apps/web` + `packages/core` + `packages/db`. Rationale: this is a learning project and the second repo in the same idiom — reusing the stack means the second build reinforces the first instead of splitting attention across two ecosystems. Patterns (facility→property scoping, RBAC-as-data, audit service, event outbox) transfer nearly one-for-one. |
| D-2 | ~~Stripe Billing vs ledger-driven charges~~ | ~~Ledger-driven PaymentIntents.~~ **SUPERSEDED BY D-11 (2026-07-31).** | Retained for history only. Do not build to this row. The original reasoning — that jurisdiction-configurable fees, proration and allocation are ours — survives into D-11; what changed is where the invoice and payment record lives. |
| D-3 | Money and time representation | **Integer cents; UTC in the DB, property-local timezone for display.** | No floats anywhere in money math. Every nightly job (charge posting, late-fee assessment, notice countdowns) runs per-property in property-local time — a late fee assessed at UTC midnight is a wrong late fee in every timezone west of London. |
| D-4 | Jurisdiction rules | **Versioned, effective-dated configuration. Texas seeded as the default; built per-state configurable.** | `JurisdictionRule` rows hold grace days, late-fee type/caps, deposit maximums and disposition deadlines, entry-notice hours, notice periods, payment-allocation order, just-cause flags, application-fee caps, RUBS permissibility. Adding a state = adding a reviewed config record + lease template, not a release. Rules apply prospectively; changing a rule never rewrites history. All legal artifacts are drafts requiring attorney review before real-world use — this is a learning project, not legal advice. |
| D-5 | Superuser accounts | **No permission bypass. The `owner` role with an all-properties assignment is the only super user.** Mirrors storage D-12. | Never add an `isSuperuser` flag or a short-circuit in `can()` / `propertyScope()` / `checkMonetaryAuthority()`. Unrestricted access is an ordinary assignment row with `roleId = owner` and `propertyId = null` — grantable, revocable, visible to the audit log. Bootstrap via a `db:create-owner` script scoped to R-007. |
| D-6 | External vendor access | **Zero-login magic-link work orders. No vendor accounts in v1.** | A vendor receives a signed, expiring link by SMS or email carrying scope, photos, address, tenant contact, and a per-work-order code reveal. Accept / propose time / upload completion photos / upload invoice all happen without an account. Rationale: the operator interview was unambiguous — a plumber with five landlord clients will not learn a sixth portal, and a maintenance module vendors won't touch has no data in it. Optional accounts for high-frequency vendors are Phase 3, never a prerequisite. |
| D-7 | Screening, e-sign, and listing syndication vendors | **Simulated adapters first, real drivers behind a partner agreement.** Follows the storage build's gate-hardware precedent (D-4 there). | `SimulatedScreeningAdapter`, `SimulatedESignAdapter`, and `SimulatedSyndicationAdapter` are the primary adapters for this build and the contract fixtures for future real drivers, including fault injection. Screening in particular is FCRA-regulated and partner-gated; a simulated provider lets the compliance workflow (criteria versioning, adverse-action generation, decision audit) be built and tested for real without a bureau relationship. Real drivers are Phase 3. |
| D-8 | Mobile strategy | **PWA, not native, for v1.** | One codebase; no app-store install wall in front of tenant activation; magic-link deep linking works cleanly. The tech's job flow gets service-worker offline caching with an IndexedDB write queue. Revisit native only if field data shows PWA offline limits being hit (R-089). SMS is the reliable notification backstop for tenants and vendors regardless. |
| D-9 | One task queue | **A single `Task` entity serves every staff work queue.** Carried over from the storage build, where seven queues had to be consolidated after the fact (its B-095). | Facility→property, type, subject entity, property-local business date, priority, assignee (nullable = anyone), status, typed proof fields, completion actor, source event id; idempotent creation on (type, entityId, businessDate). Delinquency steps, failed payments, move-out verification, inspection follow-ups, compliance items, bounced messages, and vendor no-shows are all *views* over this. Built early (R-011) precisely so nothing later invents its own. |
| D-10 | Tenant-facing lexicon | **One word per concept on every tenant-facing surface.** Mirrors storage D-15. | **home** or **unit** (not "door"), **rent**, **maintenance request** (not "ticket" or "work order" — those are staff words), **balance**, **payment**, **inspection**. Industry words — delinquency, disposition, dunning, chargeback, work order, ledger — stay on staff screens. No internal identifier (backlog ID, entity name, status enum) may render on a tenant- or vendor-reachable route, and a test asserts it. One money formatter for tenant-facing amounts. |
| D-11 | **Billing engine — supersedes D-2** (owner call, 2026-07-31) | **Stripe Billing drives recurring rent, and Stripe is the source of truth for invoices and payments.** | Each active lease gets a Stripe Customer, a Price at the lease's rent amount, and a Subscription anchored to the lease's billing day in **property-local** time (D-3 still holds — the anchor is computed locally, then expressed to Stripe). Stripe owns: invoice generation, collection, retries, ACH-return handling, invoice PDFs, and the payment record. Our `LedgerEntry` table becomes an **append-only projection** built from Stripe webhooks — still the audit surface, still exportable, but it no longer originates charges. **Deliberate divergence from the storage repo**, which stays ledger-driven per its D-6: the two projects now demonstrate the two real billing architectures, which is worth more in a learning portfolio than a second identical implementation. |
| D-12 | What stays in `packages/core` under D-11 | **Every jurisdiction-dependent calculation. Stripe executes; it does not decide.** | Late-fee amount **and its state cap clamp**, proration math for move-in/move-out, RUBS allocation, payment-allocation policy, `daysPastDue`, and deposit accounting are computed in core and pushed to Stripe as invoice items or subscription updates. Stripe has no concept of "clamp this fee to the Texas maximum," and a fee it generated is a fee we cannot defend. Rule of thumb: **if a statute could change the number, core computes it.** |
| D-13 | **Two-payer ledger shape** (owner call, 2026-08-01 — answers OQ-2, confirms OQ-12) | **The ledger is payer-agnostic from the schema up, but no voucher feature is built until OQ-2 has a firm answer.** OQ-2 was answered "unsure / possible later". | Section 8 is neither confirmed nor ruled out, so R-002 takes the low-regret option: build the shape, defer the features. Two tables carry it. `LeasePayer` is one payer of one lease — one Stripe Customer and one Subscription each, which is what OQ-12's "an invoice has exactly one payer" forces. `PayerAllocation` splits every `Charge` across the lease's payers, so the lease still shows **one balance**. An ordinary lease is exactly one `LeasePayer` carrying the whole charge: **one code path, not two** — allocation always happens. Nothing in the schema knows what a housing authority is beyond a `PayerType` value. The voucher *features* — recertification proration, bulk HAP deposit reconciliation across many tenant ledgers, abatement, HQS re-inspection deadlines, and "dunning never pursues the HAP portion" — remain **R-048's and remain gated on OQ-2**. Rationale: the schema affordance costs a column and a join; retrofitting a split payer onto a single-payer ledger costs every financial query and a data migration. |

## How to use this log

When starting a Claude Code session on a backlog item, include this file alongside the relevant PRD section. If an item's PRD text contradicts a decision here, the decision wins. New conflicts discovered during the build should be appended here with a new D-number rather than resolved silently. An item whose gating question above is unanswered should not be started — build to the PRD's stated default and record the assumption, or pick a different item.
