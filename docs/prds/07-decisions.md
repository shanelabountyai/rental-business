**Status:** D-1 through D-10 recorded 2026-07-31 at project setup, carrying forward the conventions proven on the self-storage build. **D-11 (2026-07-31) supersedes D-2** and deliberately diverges from the storage platform. **D-13 (2026-08-01) settles the two-payer ledger shape** and closes OQ-12; OQ-2 is partially answered and R-048 remains gated on the rest of it. **D-14 (2026-08-03) settles file/photo storage** for R-012. **D-15 (2026-08-05) settles notification delivery providers** for R-016 and flags the 10DLC registration as the owner's longest external lead time. **D-16 (2026-08-05) amends "single-use" for vendor links only** — they are multi-use until expiry, for R-025. **D-17 (2026-08-06) answers OQ-3** — all external vendors, so R-028 defers to Phase 3. Open owner decisions are listed under "Needs owner decision"; several gate specific milestones.
**Precedence:** This document amends the PRDs. Where a PRD conflicts with a decision below, this document wins. When building from the backlog, treat each decision as settled — do not re-open unless the owner amends this log.

| D-13 | **Two-payer ledger shape** (owner call, 2026-08-01 — answers OQ-2, confirms OQ-12) | **The ledger is payer-agnostic from the schema up, but no voucher feature is built until OQ-2 has a firm answer.** OQ-2 was answered "unsure / possible later". | Section 8 is neither confirmed nor ruled out, so R-002 takes the low-regret option: build the shape, defer the features. Two tables carry it. `LeasePayer` is one payer of one lease — one Stripe Customer and one Subscription each, which is what OQ-12's "an invoice has exactly one payer" forces. `PayerAllocation` splits every `Charge` across the lease's payers, so the lease still shows **one balance**. An ordinary lease is exactly one `LeasePayer` carrying the whole charge: **one code path, not two** — allocation always happens. Nothing in the schema knows what a housing authority is beyond a `PayerType` value. | D-14 | File/photo storage (R-012) | **A `StorageAdapter` interface, backed by local disk in dev/test; a real object store (Vercel Blob/S3-class) is a same-interface swap, not a rewrite, whenever this deploys somewhere the filesystem isn't durable across instances.** | Unlike D-7's simulated adapters, storage is not partner-gated or regulated — it is commodity infrastructure (master PRD §7: "Buy") that can run for real against disk today. `LocalDiskStorageAdapter` writes under `DOCUMENT_STORAGE_PATH` (default `.data/documents/`, gitignored); every caller goes through `StorageAdapter.put/get/delete`, never `fs` directly, so the swap touches one file. EXIF `capturedAt` is extracted and stored distinct from `createdAt` and is never stripped — a photo's timestamp is the evidence (PROP-08, master PRD §5). Client-side compression and resumable/chunked upload (both named in DOC-01 and §6.5) are deliberately NOT built yet: server-side single-shot upload via a plain file input covers correctness for typical photo sizes on a decent connection; the mobile-3G stress case is a real gap, left for whoever revisits upload UX with field data in hand. |

| D-15 | Notification delivery providers (R-016) | **A `ChannelAdapter` interface with a logging adapter wired today; Resend and Twilio are a same-interface swap, blocked on external workstreams the owner has to start — a verified sending domain and an approved 10DLC campaign.** Every other guarantee of the engine — idempotency, preference resolution, quiet-hours deferral, kill switch, sandbox redirect, the append-only log — is built and tested for real against the logging adapter. | The same shape as D-14, arrived at for a different reason. Storage is commodity infrastructure that *could* run for real against disk on day one, so D-14 ran it. Email and SMS are equally commodity but *cannot* run at all yet: Resend needs a domain with SPF/DKIM published, and Twilio will not deliver to a US mobile number without an approved 10DLC brand and campaign, which takes days to weeks. Writing an HTTP client that has never once been executed — against an account that does not exist — produces code that looks finished and is untested, which is strictly worse than an honest seam. So the seam is the deliverable, and the two provider drivers are a later, small, genuinely-testable change to one assignment in `apps/web/lib/notifications/provider.ts`. **Two controls make an enabled-by-default engine safe in the meantime and are not optional in any non-production environment**: `NOTIFICATIONS_ENABLED=false` stops all sending without a deploy (notifications are still decided and recorded as suppressed, so nothing is lost), and `NOTIFICATIONS_SANDBOX_TO` redirects every send to one address while preserving the intended recipient on the record — which is what prevents a laptop pointed at a copy of production data from texting real tenants. **The 10DLC registration is the long pole and should be started now**, per the backlog's own note; nothing in the code can shorten it. |

| D-16 | **Vendor magic-link lifetime (R-025)** — amends "single-use" in ROLE-05, §6.1, §7 and §13 | **A vendor work-order link is scoped, expiring and revocable, but MULTI-USE until it expires — not single-use.** Single-use remains correct and unchanged for every other token purpose (tenant magic link, both password resets, the MFA challenge). | The PRD's "single-use" is right for a token whose job is to **establish** a longer-lived credential: a tenant magic link is redeemed once and becomes a session, so burning it costs the user nothing. A vendor link **is** the credential — there is no account and no session behind it (D-6) — so burning it on first click means the plumber who opened the text at 7am to accept the job cannot reopen it at 4pm to upload the invoice. That is not a hypothetical edge: accept-now / photograph-the-work-later / photograph-the-napkin-invoice-later is the *only* real vendor workflow, and it spans hours or days by nature. A single-use link would fail on the second step of every single job, and "the vendor phones the invoice in instead" is precisely the outcome D-6 exists to prevent — the backlog's own line for R-025 calls this item "the difference between a maintenance module vendors use and one they ignore." **The alternative considered and rejected** was single-use redemption into a work-order-scoped session cookie: it preserves the letter of "single-use" but dies on a cleared cookie, a second device, or simply re-clicking the original SMS days later, which is the most likely way a vendor returns. **What replaces single-use as the control set**, all of it built: the token is scoped to exactly ONE work order and grants nothing else anywhere in the product; it expires (3 days, `TOKEN_TTL_MINUTES.VENDOR_WORK_ORDER`); reissuing revokes every prior token for that work order, so a link believed compromised is killed by resending; every privileged action taken through it is audited with the vendor named as actor; and each access-code reveal is logged individually (PROP-03). Worth stating plainly: the status quo this replaces is an operator texting the address, gate code and tenant's phone number in cleartext with no expiry, no scope and no audit trail whatsoever — the link is strictly better than what it is displacing, on every one of those axes. |

| D-17 | **OQ-3 answered: all external vendors** (owner call, 2026-08-06) — closes OQ-3 | **There is no in-house maintenance tech. Every job goes to an external vendor, so the zero-login magic link (D-6, R-025) IS the entire maintenance edge.** R-028's offline tech PWA moves to Phase 3. | The backlog's own risk note 3 anticipated this: "If OQ-3 answers 'all external vendors,' R-028 is a Phase 3 item and Milestone 2 shortens by an L." That is what happened. **Why deferring is right rather than merely cheaper**: R-028 exists for somebody on payroll standing in a basement with no signal — cached job list, IndexedDB-queued status changes and photos, sync on reconnect. A vendor holding a magic link needs none of it: the link works on any phone, needs no install, and if signal drops they reload it later, which is exactly the multi-use behaviour D-16 already guarantees. Building a service worker, an offline queue and a sync-conflict policy for a persona that does not exist would be the most expensive wrong turn available in this backlog. **What this does NOT defer**: MAINT-06's "required completion photo" is already built into R-025's vendor upload, and R-030's verify-and-close depends on work orders reaching WORK_COMPLETE, which the vendor path already does — so R-030's listed dependency on R-028 is soft and does not block it. **Reversible**: if an in-house tech is ever hired, R-028 returns as a self-contained item; nothing built since R-024 assumes its absence, and `assignWorkOrder()` still supports staff assignment because a manager doing a job themselves is not the same as a maintenance employee. |

| D-18 | **After-hours routing without an answer to OQ-10 (R-029)** | **The rota is self-service and the fallback is to page EVERYBODY. Nobody on call for a property means an emergency there reaches every staff member who can act on it — narrowing is earned by somebody taking responsibility, never assumed.** Escalation fires at everyone not already paged, all at once, 15 minutes after an unacknowledged emergency; there is no ranked, tier-by-tier chain and no priority column behind one. | OQ-10 ("who is on-call today, and what is the actual protocol?") is still open, and the backlog is right that "the escalation chain encodes a real human arrangement; inventing one produces an escalation path nobody answers." So R-029 deliberately encodes **no** arrangement. It provides the mechanism — a window a person opens on themselves, an acknowledgement that stops the clock, a chain that reaches everybody else — and lets the operator's real protocol be whatever they actually do. **Why the fallback pages everybody**: this is R-026's commitment held. R-026 measured that paging every `ticket.write` holder was making emergency submission slow and recorded that capping recipients "would be a safety regression dressed as a performance fix: paging one person too few during a gas leak is not symmetrical with one too many." A rota narrows that set honestly, because somebody volunteered; a lapsed or never-configured rota must not, and the basis (`on_call_rota` vs `no_rota_paging_everyone`) is recorded on every escalation so a gap reads as a gap rather than as a working rota. **Why no tiered chain**: MAINT-12 says "page → SMS → call → backup", and three of those four are channels the notification engine already sends simultaneously. A rank column would have ordered a list that is paged all at once — a field somebody would maintain believing it changed something. Build tiering the day escalation actually waits between tiers, and not before. **Why self-service only**: putting yourself on call is volunteering, not a privilege, so it needs no permission; putting somebody *else* on call is a privilege and this cannot do it — the row written is always the actor's own. A rota screen where one person schedules the team is a real thing to want and needs a real permission. **Re-ask OQ-10 anyway** before assuming the chain matches reality: if the true protocol is "the owner's phone, always, and the PM only during business hours", that is a scheduling UI on top of this mechanism, not a change to it. |

| D-19 | **Verify & close: where the money is entered, and who owns a reopen (R-030)** | **The cost of a job is typed ONCE, on the work order, and every downstream reader computes from that row — there is no maintenance-spend table and never will be one.** A tenant's verification is its own append-only-in-practice row carrying **the vendor who did the work, captured at the moment of the answer**, not read off the work order later. Closing is refused over a live "not fixed" and permitted without any answer at all, with the absence recorded. | Three things, each of which a later session could plausibly get wrong. **(1) One place for the money.** The backlog calls the WO → invoice → P&L chain "the specific place owners abandon software", and the reason it breaks elsewhere is always the same: somebody types the invoice total a second time into the books, the two copies drift, and neither can be trusted again. So `closeWorkOrder()` writes `invoiceCents` onto the work order and the property's maintenance spend is a projection of those rows through `jobCostCents()` — the same function R-026's re-approval check uses, so "what did this cost" cannot mean two numbers on two screens. R-042's QuickBooks export must MAP from these rows, not ask anybody to re-enter them. **(2) The vendor is captured on the answer.** MAINT-07 says reopen rate is tracked "from day one" and this is what that costs: a reopened job is normally reassigned, so by the time anybody runs a vendor report the work order names whoever eventually fixed it. Reading attribution off the work order would credit the second vendor with the first one's failure, and once the column has moved no later analysis can recover it. `WorkOrderVerification.vendorId` is written when the tenant taps, and the reopen-rate report reads only that. There is a test that reassigns mid-flow and asserts the failure stays with the first vendor. **(3) The two close refusals are asymmetric on purpose.** A tenant's current-round "no" blocks the close outright — a live complaint recorded as resolved is what a tenant later shows a judge, and it outranks every bookkeeping concern in the ordering. But *silence* does not block: a tenant who never replies must not be able to hold a work order open forever, so the close proceeds and `workorder.closed` records `unverified: true`, which the work order page then states permanently rather than as a toast. A $0 close needs an explicit "this job cost nothing", because a job closed at nothing by accident is a hole in a property's cost history nobody notices until a year of spend is quietly wrong. **What R-030 deliberately did NOT build**: the `INVOICED` status and MAINT-09's vendor-visible invoice lifecycle (received → approved → paid) belong to R-079's vendor management, and the chargeback that a `tenantCaused` close makes possible is R-031's — this item sets the flag and posts nothing to any ledger. |

| D-20 | **Work-order comms threading: what stays continuous, what gets scoped, and why an "attach" cannot be an update (R-032)** | **The tenant's thread stays the ONE continuous conversation per tenancy R-017 built (COMM-01); individual Messages are tagged with `ticketId`/`workOrderId` at send time instead. The vendor gets a genuinely SEPARATE, work-order-scoped thread (`vendor:<id>:workorder:<id>`), alongside the unchanged property-scoped thread inbound SMS already routes into. Attaching an existing untagged message to a job afterward is a new `WorkOrderMessageLink` row, never an update to the message.** | Three calls, each forced by something already built. **(1) The tenant thread does not fragment per ticket.** COMM-01's whole point was one continuous history, and re-litigating that to satisfy COMM-06 would break the earlier decision instead of building on it. Tagging individual messages is additive and costs nothing when absent. **(2) The vendor DOES get a new per-job thread**, and this is not the same call - D-16 already scopes a vendor's magic link to exactly one work order, and a vendor with two concurrent jobs for this operator (ordinary for a preferred trade) must not have both conversations arrive in one mixed thread. `threadKey()`'s VENDOR case now branches on whether a `workOrderId` is supplied: absent, the key is unchanged (`vendor:<id>:property:<id>`, still what inbound SMS resolves to, since a text has no way to say which job it is about); present, it is a new, different key. Nothing that existed before this item changes shape. The new thread is PORTAL-only by construction - offering SMS on it would let a vendor's reply land in the OTHER (property-scoped) thread instead, silently splitting one conversation into two nobody reads together. **(3) "Attach this stray message to a job" cannot touch the Message row**, discovered only after building it the update way first: `Message` has been append-only since R-017 (`Message_append_only` rejects every UPDATE, not only DELETE), so `Message.ticketId`/`workOrderId` are `RESTRICT`, not the Prisma-default `SET NULL` - a `SET NULL` cascade would require exactly the UPDATE the trigger exists to refuse. `WorkOrderMessageLink` is an insert-only join table instead: a message that already existed gets a new row pointing at the job, and the original evidence is never rewritten. The unique constraint on `messageId` is what keeps a message from being claimed by two jobs at once. |

## How to use this log

When starting a Claude Code session on a backlog item, include this file alongside the relevant PRD section. If an item's PRD text contradicts a decision here, the decision wins. New conflicts discovered during the build should be appended here with a new D-number rather than resolved silently. An item whose gating question above is unanswered should not be started — build to the PRD's stated default and record the assumption, or pick a different item.
