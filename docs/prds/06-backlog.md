# 06 — Prioritized Product Backlog

**Product:** Single-family rental operations platform (10–50 units, multi-entity)
**Status:** v1.0 — 2026-07-31
**Sources:** `00-master-prd.md` (single master PRD; §5 holds the epics and acceptance criteria), `07-decisions.md`

This is the single, strictly-ordered build backlog. Items are sequenced so that every item is buildable when reached (all dependencies appear earlier), foundation comes first, and the shortest path runs to the two golden paths: **(1) a tenant reports a leak from their phone, it reaches a vendor by text with photos, the vendor closes it with a photo and an invoice, and the cost lands on the property's books** (end of Milestone 2) and **(2) rent posts, autopay collects it, a delinquent lease accrues a jurisdiction-correct late fee, the reminder ladder fires, and the owner sees all of it on one rent roll** (end of Milestone 3). Numbering is global and continuous across milestones.

Sizes: **S** ≈ one short session, **M** ≈ one focused session, **L** ≈ 2–3 sessions or one long one, **XL** ≈ should be split during planning. Phase = the phase the feature belongs to per the PRD. A ✅ on the ID means the item is built and committed.

**Numbering.** R-numbers are global, continuous and permanent — never renumbered, never reused. The **#** column is positional. Rows added later carry a letter (`16a` = inserted between 16 and 17) so inserting an item does not renumber seventy rows below it. The `R-` prefix distinguishes this repo from the storage platform's `B-` series; the conventions are otherwise identical.

**Story IDs.** The PRD/Feature column points at `00-master-prd.md` §5 story IDs (PROP-, LEASE-, PAY-, MAINT-, COMM-, INSP-, DOC-, RPT-, NOTIF-, ROLE-, RISK-). Those IDs are the authoritative acceptance criteria — the row here is the work order, the PRD story is the definition of done.

## How to use this backlog with Claude Code

- **Work strictly top to bottom.** The order encodes the dependency graph; when you reach an item, everything it depends on is already built. Don't cherry-pick a later item unless its entire "Depends on" chain is done.
- **One item (or one small cluster) per session.** S/M items are a single focused session. L items should be split into 2–3 sessions at the start ("build the state machine," then "build the UI on it"). R-097 (XL) must be split before starting.
- **Load the source PRD section as context.** The PRD/Feature column points at the authoritative story in `00-master-prd.md` §5. That story's Given/When/Then criteria are the item's definition of done — not this row's prose, which is the work order.
- **Start each session with:** the backlog row, the PRD story, `07-decisions.md`, the cross-cutting requirements in PRD §6 (auth, WCAG 2.1 AA, mobile-first, PCI scope, jurisdiction config), and the current schema. End each session with tests passing — **money math, jurisdiction-rule resolution, and the maintenance funnel are the three places tests are non-negotiable** — and the seed script updated if entities changed.
- **Check the gate before starting.** If the item's row or `07-decisions.md` names an unanswered OQ, either get the answer or build to the PRD's stated default and record the assumption in `PROGRESS.md`. Don't decide it silently.
- **Two demo checkpoints:** after R-032, run Golden Path 1 (leak text → vendor magic link → closed with photo → cost on the property). After R-050, run Golden Path 2 (rent posts → autopay collects → late fee → reminder → magic-link payment → owner dashboard).

## Rationale: ordering decisions & trade-offs

1. **Foundation before any feature (R-001–R-013).** Every module reads and writes the shared schema and assumes property scoping, RBAC, audit logging, an event bus, and jurisdiction rules. Building these once, first, prevents each module re-inventing them.
2. **The jurisdiction-rules engine is foundation, not a compliance feature (R-010).** It is deliberately the largest Milestone 1 item. Every later module reads statutory numbers from it; if it arrives late, dozens of hardcoded grace periods and deadlines have to be hunted down, and the ones missed are silent. Its resolver signature — `rulesFor(property, asOf)` — is what makes rule changes prospective rather than retroactive.
3. **The task queue before its first consumer (R-011).** The storage build had to consolidate seven separate queues after the fact. This is that lesson spent once, in advance, for the cost of building R-011 before anything needs it.
4. **Maintenance is Golden Path 1, ahead of money.** Two reasons. It forces the five hardest *shared* subsystems into existence early — notification engine, comms threading, photo evidence, magic-link identity, task queue — which the money loop then inherits rather than builds. And it is the differentiated 30% that justifies a custom build at all: rent collection is available off the shelf; a vendor who fixes things by text without an account is not. Building it first also means the riskiest adoption assumption (D-6, vendors will use magic links) gets tested in week 6 rather than month 5.
5. **Stripe Billing owns collection; core owns every number a statute could change (R-034, R-035; D-11/D-12).** Delegating invoicing, retries and ACH-return handling removes a genuine pile of scheduler code, and it is the more common architecture in industry — worth learning deliberately, which is why this repo diverges from the storage platform rather than repeating it. The discipline that makes it safe is the split: Stripe executes, core decides. A late fee Stripe generated is a late fee that ignores the state cap, and a fee that ignores the state cap is one a tenant's lawyer gets to talk about. The projection is built from webhooks and **reconciled on a schedule with drift alarmed** — the failure mode of an event-sourced read model is silent divergence, and money that silently diverges is the worst bug this system can have.
6. **Notices and evidence get their own milestone (R-051–R-055).** Proof-of-delivery, immutable transcripts and the retaliation guard are uniform requirements across leasing, billing and maintenance. Building them as a milestone rather than per-module is why the eviction packet (R-083) and the deposit disposition (R-071) are later assembly jobs instead of new plumbing.
7. **Leasing after the operating core.** Leasing events happen 10–20 times a year; maintenance happens weekly and rent monthly. Leasing also carries all three external integrations, so it benefits from landing on a stable base — and its simulated adapters (D-7) mean an unavailable screening partner never blocks the build.
8. **Screening's compliance machinery is built even though the provider is simulated (R-060, R-061).** Criteria versioning, order-of-application processing, decision audit and adverse-action generation are the parts with legal consequence, and they are fully testable against a simulator. Swapping in a real bureau later is a driver, not a redesign.
9. **Risk workflows are Phase 2, deliberately, with two exceptions.** Habitability auto-elevation (R-023) and the retaliation guard (R-055) ship in MVP because both are cheap once the comms record exists and both are existential if absent. The rest — abandonment, VAWA, SCRA, ESA, hoarding — are real but rarer, and each is a case file over machinery MVP already built.
10. **Real vendor drivers last (R-093).** Following the storage build's precedent: partner-gated integrations are the wrong thing to be blocked on in a learning project, and a simulator with fault injection is a better test fixture than a sandbox you don't control.

## Flagged gaps & conflicts

Unlike the storage backlog at the same stage, this list is short — there is one master PRD rather than six, so most cross-document conflicts don't exist. What remains:

1. **Autopay and partial payments are mutually exclusive under D-11 (OQ-11) — this blocks Milestone 3.** Stripe supports partial payments only on `send_invoice` subscriptions, not `charge_automatically` ones, and PAY-02 (autopay) and PAY-03 (partial allocation) are both Must. This was discovered after D-11 was taken and is a documented product limit, not a design preference. Resolve it before R-037 starts; if the honest answer is "we need both, natively," that is a reason to re-open D-11, not to half-build it.
2. ~~**Section 8 phasing (R-048).**~~ **Schema half closed 2026-08-01 (D-13).** R-002 shipped the payer-agnostic ledger, so the expensive retrofit this risk warned about can no longer happen. The remaining risk is only phasing: PAY-13 is Must-if-present / Should-if-not and OQ-2 answered "unsure", so R-048 is still unschedulable. That is a planning question now, not an architectural one.
3. **Offline tech flow vs all-vendor operation (R-028).** If OQ-3 answers "all external vendors," R-028 is a Phase 3 item and Milestone 2 shortens by an L. The item is currently sequenced as if an in-house tech exists.
4. **Screening cannot start without written criteria (OQ-6).** This is a hard block, not a preference: R-060's entire fair-housing posture is "apply documented criteria uniformly and prove it." Absent criteria there is nothing to version.
5. **Spanish surface may be Must, not Phase 3 (OQ-9).** R-096 is sequenced as Phase 3 on the assumption of a predominantly English-speaking tenant base. If that is wrong, it moves into Milestone 2 alongside the portal shell, because retrofitting localization after fifty templates exist is the expensive order.
6. **Deposit-deadline automation is a liability if the config is wrong (R-071, R-010).** The system enforcing a countdown means the system can enforce the *wrong* countdown at scale. Legal review of each jurisdiction config before activation is a release gate, not a nice-to-have — recorded here because it is a process requirement no code review will catch.
