## The Business Problem

A single-family rental owner running 10–50 houses across several LLCs is doing the job from spreadsheets, personal text threads, email, Dropbox and a paper lease binder. Every dispute — a withheld deposit, an eviction, a habitability complaint, a fair-housing claim — turns on "who said what, when, and can you prove it," and none of those tools keep proof. Grace periods, late-fee caps, deposit deadlines and notice periods vary by state and city, so a spreadsheet formula that's right for Texas is a liability in Colorado. And half the people who need to use the system won't install anything: a vendor doing a repair will not create an account, and a tenant on a flip phone still needs a way to pay rent and report a leak.

## What I Built

- **Renters get a portal and a full non-digital fallback.** Applications, e-signed leases, rent payment (autopay or per-invoice), maintenance requests with photos, and messages — or the same things done by a staff member on their behalf, because the PRD treats "tenant has no smartphone" as a requirement, not an edge case.
- **Vendors work by text link, never an app.** A work order arrives as a magic link — no login, no install — and closes out with photos and an invoice from the same link.
- **Staff run the whole operating loop**: leasing and screening, maintenance triage and dispatch, rent collection and delinquency, inspections and move-in/move-out condition reports, deposit disposition, notices and evictions, and one shared task queue instead of a queue per module.
- **Every statutory number is configuration, not code.** Grace periods, late-fee caps, deposit deadlines and entry-notice hours are versioned, effective-dated `JurisdictionRule` rows per property — Texas is seeded, every other state is a data entry, not a redeploy.
- **The evidence trail is the product.** Every message, notice, photo, payment and approval is timestamped, append-only (enforced by a Postgres trigger, not application code) and exportable as a court-ready packet — the eviction packet and the deposit disposition are assembly jobs over that record, not new plumbing.
- **Stripe is the system of record for money.** `LedgerEntry` is an append-only projection built from Stripe webhooks, reconciled hourly against the event log with drift surfaced rather than assumed away — and every number a statute could change (late fees, proration, allocation order) is computed by the app and pushed to Stripe, never generated by it.

## How It's Built

It's an npm-workspaces monorepo: `apps/web` (Next.js App Router), `packages/core` (domain logic — money math, jurisdiction rules, metrics) and `packages/db` (Prisma schema + hand-written migrations). The schema has 111 models across 114 migrations, using the canonical entity names from the master PRD (LegalEntity, Property, Unit, Lease, Tenant, LedgerEntry, WorkOrder, Notice, Task and supporting entities). Three external capabilities that are partner-gated or regulated — screening, e-sign, listing syndication — run against fault-injecting simulators until a real vendor is chosen; Stripe, Twilio and Resend are real, wired drivers behind the same kind of seam, selected by whether a key is configured rather than by an environment flag.

**Key design decisions** (the full log is [`docs/prds/07-decisions.md`](docs/prds/07-decisions.md): 253 entries, each settled once)

| Decision | Alternative considered | Why I chose it |
|---|---|---|
| Stripe Billing owns collection; `packages/core` computes every statute-dependent number and pushes it to Stripe (D-11, D-12) | Let Stripe's subscription engine generate late fees and proration directly | A late fee Stripe generated on its own would ignore the state's cap — the split ("Stripe executes, core decides") is what keeps a statutory number under version control instead of inside a billing vendor's black box |
| Jurisdiction rules are versioned, effective-dated data (D-4), with no hardcoded default | Ship Texas defaults everywhere and let an operator override | A default is a legal claim about a state the software was never told about — an unconfigured jurisdiction runs no fee, no deadline, and says so on screen |
| One `Task` entity serves every staff work queue (D-9) | A queue per module (maintenance, leasing, compliance) | The storage build had to consolidate seven separate queues after the fact — this is that lesson spent once, in advance |
| Money-and-message tables (`LedgerEntry`, `AuditLog`, `Message`, `Notification`) are append-only, enforced by a Postgres trigger | Application-level convention ("just don't update these") | Nothing can edit or delete a row of evidence, including a bug and including me — covered under *Defects Found* |
| A stored document is served through one allowlisted-content-type helper (D-137) | Return the browser-supplied `Content-Type` as uploaded | `image/svg+xml` served inline is a script running in this app's origin under a stranger's session token — four routes had hand-rolled this response and all four had the hole |
| A `BusinessDate` is typed and formatted only inside the renderer, never at the call site (D-153, D-154) | Format the date wherever it's read | A raw `2026-08-01` reached a tenant in an SMS for as long as the template existed, because the predicate that finds this bug class matches the field's *name*, not whether it was actually wrapped |

## Skills Learned / Functions Unlocked

- **Compliance rules as versioned configuration.** Every grace period, late-fee cap and deposit deadline reads from `JurisdictionRule`, resolved as of a date rather than hardcoded — the resolver signature (`rulesFor(property, asOf)`) is what makes a rule change prospective instead of retroactive. See [`apps/web/lib/jurisdiction/queries.ts`](apps/web/lib/jurisdiction/queries.ts).
- **Event-sourced money with a reconciled projection.** Stripe webhooks are the write path; the ledger is a read model checked hourly against the event log, with drift reported rather than assumed away. See [`apps/web/lib/ledger/reconcile.ts`](apps/web/lib/ledger/reconcile.ts) and [`apps/web/lib/billing/webhook.ts`](apps/web/lib/billing/webhook.ts).
- **A magic-link identity model for people who will never create an account.** Vendors and offline tenants work entirely through signed, scoped, expiring tokens — no password, no app install. See [`apps/web/lib/vendors/link.ts`](apps/web/lib/vendors/link.ts).
- **An append-only evidence trail enforced at the database, not in application code.** Corrections are reversing entries; a foreign key into one of these tables has to be `onDelete: Restrict` or the cascade itself gets refused at runtime — a mistake fixed twice on this build alone. See `packages/db/prisma/migrations/*append_only*`.
- **A notification engine every module routes through**, with quiet-hours deferral, per-category preferences and one delivery record — rather than five modules each hand-rolling their own send. See [`apps/web/lib/notifications/`](apps/web/lib/notifications/).
- **WCAG 2.1 AA as an acceptance criterion**, not a later pass, on every tenant- and vendor-facing screen — the e2e suite runs axe at phone and desktop widths on every route it touches.

## The Hardest Bug

**No tenant could ever sign in, on any deployed environment, for seventeen months.** `apps/web/lib/auth/delivery.ts` was written as a placeholder on day one (R-003), with a comment saying *"R-030 replaces this"* — and a guard that silently no-op'd in production:

```ts
if (process.env.NODE_ENV === 'production') { console.warn(…); return }
```

R-030 built the real notification engine. R-104 wired Resend and Twilio into it. Neither touched this file. Because `tenant-magic-link` is the *only* tenant sign-in provider this product has, the bug meant no tenant magic link and no staff password reset had ever left a deployed environment — a total, silent lockout of every real user the product has, hiding in plain sight since the very first commit.

It stayed hidden for three reasons that each independently masked it: local development printed the link to the console, so every local demo walk worked perfectly; the e2e suite asserted that the *flow* completed, never that a message was actually *sent*; and the one send that got watched — the vendor work-order link — goes through a completely different module (R-025's own), so it kept working while the identical-looking tenant path was dead. A later item (R-138, building the staff invite) tripped over it by accident, filed it, and R-139 took it immediately because it was bigger than the item that found it.

The fix routes `deliverAuthLink` through the real notification engine — the same `notify()` plus a *scoped* dispatch that R-025's vendor path already used, so a person standing at a login form doesn't wait for the hourly cron and doesn't pay for the whole queue ahead of them. The regression test lives in `e2e/staff.spec.ts`, deliberately, because the bug only existed in a production build — a dev-server or unit-test assertion could never have seen it, since the branch that skips the send checks `NODE_ENV === 'production'` and nothing else in the suite runs under that flag.

**What I'd instrument next time:** any `NODE_ENV === 'production'` branch that returns early is a deploy-only code path by definition, and a deploy-only code path needs a production-build assertion the day it's written, not seventeen months and a different item's accident later.

## Defects Found

Each of these cost a debugging pass. The lesson from each is written into the repo's `CLAUDE.md`, so the next session does not repeat it.

- **A shipped bug reintroduced by trying to fix a different one.** `invoice.payment_succeeded` looked like the right Stripe webhook to book a payment on, until it turned out Stripe never sends it for an invoice paid out of band — so every offline check, money order and cash payment recorded since the ledger shipped had pushed to Stripe correctly and never once reached the books. The fix (`invoice.updated`, the one event every money path shares) is now flagged in the code as a bug that would reintroduce itself if swapped back.
- **A routed message silently went nowhere for four backlog items.** Every inbound-email test used `from: 'tenant@example.test'` — no real mail client sends a bare address, they all send `Display Name <tenant@example.test>` — so nothing unwrapped the display name and routing matched no tenant. It looked exactly like mail from a stranger, which is what that queue is *for*, so it survived four separate items before anyone noticed.
- **A framework patch version turned four latent test bugs red at once.** Next's own route announcer duplicates every page heading into a `role="alert"` div for accessibility; a minor Next bump made two copies of a heading land in the same paint for the first time, and every assertion written against the wrong locator failed simultaneously — nothing in the app had changed.
- **An `afterAll` cleanup query with no `ORDER BY` was silently non-deterministic.** A leftover fixture row from an earlier crashed run tied with a live test's fixture on the same lookup key; which one won was query-planner order, not code — so three tests failed roughly one run in three, with wrong *data* and no thrown error, for two backlog items before it was root-caused.
- **A green CI pipeline was reported as still broken for eleven consecutive items.** After a nine-day GitHub Actions billing outage was fixed, eleven backlog entries in a row copied forward the previous entry's "still unresolved" line instead of checking `gh run list` — the same failure as the original outage, wearing the opposite sign: first a dead pipeline nobody read, then a live one nobody read.
- **A database connection cap was removed once "to speed things up" and made the suite slower.** Two process-parallel test runners against a 100-connection Postgres instance were arithmetically guaranteed to exhaust it under load; the resulting `too many clients already` errors surfaced inside whichever fixture happened to be seeding at the time, which read as three unrelated flaky tests before anyone counted `pg_stat_activity`.

## What I'd Do Differently

- **A deploy-only code path is not covered by "the tests pass."** The seventeen-month auth outage above is the clearest example: `npm test` and the e2e suite were both green the entire time, because neither ever ran under `NODE_ENV=production`. I'd now write the production-build assertion in the same item that adds the environment branch, not wait for it to be found.
- **A value that reads correctly is not the same as a value that's formatted correctly, and the difference hides from a text-based grep.** The `BusinessDate` formatting rule exists because a field named `paidOn` can be perfectly correct data and still reach a tenant unformatted in a live SMS — the bug is invisible to any search keyed on the field's name rather than on whether a formatter actually touched it on the way out.
- **Trust the pipeline by reading it, not by copying yesterday's status line forward.** Both CI incidents above — the real nine-day outage and the eleven-item false "still broken" that followed it — are the same root cause: a status claim that nobody re-verified. `gh run list --limit 5` costs three seconds; assuming costs a debugging session, or eleven items of misplaced confidence.
